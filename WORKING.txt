  1. WHAT IS AGRITWIN?
────────────────────────────────────────────────────────────────────────────────

AgriTwin is a full-stack, IoT-based Digital Twin platform for small-scale
precision agriculture ("micro-farming"). It mirrors a physical growing
environment — temperature, humidity, light, soil moisture — inside a software
physics model that runs in real-time alongside the real sensors.

Key actions the system performs continuously:

  • Collects sensor data from an ESP32 every 10 seconds via MQTT
  • Stores readings in SQLite on a laptop (cloud layer)
  • Runs a physics-based digital twin that predicts what the sensors will
    read next and computes evapotranspiration, water deficit, and GDD
  • Compares the prediction to the actual sensors and tracks accuracy
  • Serves a Next.js web dashboard with live gauges, 96-frame plant animation,
    and history charts
  • Answers natural-language questions about the farm via LLaMA 3 AI
  • Controls a water pump and grow light via MQTT relay commands
  • Captures webcam images every 5 minutes from the Raspberry Pi
  • Pushes all data to a Flutter mobile app with offline caching


────────────────────────────────────────────────────────────────────────────────
  2. WHY IT WAS BUILT — PROBLEM STATEMENT
────────────────────────────────────────────────────────────────────────────────

Problem
-------
Small-scale farmers and hobbyist micro-farms have no affordable, integrated
system that:
  (a) monitors soil + climate sensors in real time
  (b) uses a physics model to predict future crop stress
  (c) provides AI-powered diagnosis and recommendations
  (d) works on low-cost commodity hardware (ESP32 ~$3, Pi Zero ~$15)
  (e) runs entirely on-premises — no paid cloud subscription

Commercial alternatives
-----------------------
  • John Deere Operations Center  — enterprise, expensive, proprietary hardware
  • FarmBeats (Microsoft)         — research prototype, not productized
  • CropIn, Taranis               — subscription-based, no local control
  • Grafana + InfluxDB            — generic monitoring, no farm physics

AgriTwin fills the gap by combining IoT edge computing, fog buffering,
physics-based digital twin simulation, and local AI — all open-source,
all on hardware that costs under $30 total.

────────────────────────────────────────────────────────────────────────────────
  4. LAYER 1: EDGE — ESP32 FIRMWARE
────────────────────────────────────────────────────────────────────────────────

Hardware
--------
  • Board: ESP32-DevKitC (Espressif ESP32, dual-core Xtensa LX6, 240 MHz)
  • RAM: 520 KB SRAM
  • Flash: 4 MB (with OTA partition table: 2 × 1.875 MB app slots)
  • Connected via USB (COM3) for upload; runs standalone on 5V USB power

Firmware version: 1.1.0
File: edge/src/main.cpp
Platform: PlatformIO + Arduino framework

Sensors and Actuators
---------------------
  GPIO 4  — DHT11 digital sensor
              Measures temperature (0-50°C ±2°C) and relative humidity (20-90% ±5%)
              One-wire protocol at 1Hz max update rate
              Why GPIO 4: simple digital GPIO, not on ADC1 or ADC2

  GPIO 33 — LDR (Light Dependent Resistor)
              10kΩ pull-down to GND, LDR to 3.3V
              ADC1 channel 5. 0-4095 raw → mapped to 0-100% light level
              Formula: lightPercent = map(analogRead(33), 0, 4095, 0, 100)
              Why GPIO 33: ADC1. ADC2 (GPIO 0,2,4,12-15,25-27) conflicts with WiFi

  GPIO 34 — Capacitive soil moisture sensor
              ADC1 channel 6. Input-only pin (no internal pull-up/down)
              Outputs ~3.0V in air (dry), ~1.2V in wet soil
              Calibrated: dry=3000 raw → 0%, wet=1200 raw → 100%
              Formula: soilPercent = map(raw, dryVal, wetVal, 0, 100)
              Why GPIO 34: ADC1, input-only — ideal for analog sensor

  GPIO 26 — Water pump relay (active-LOW)
              Relay HIGH = pump OFF, relay LOW = pump ON
              Controlled by auto-mode or MQTT command
              Why GPIO 26: standard GPIO output, not boot-sensitive

  GPIO 25 — Grow light relay (active-LOW)
              Same logic as pump relay
              Why GPIO 25: adjacent to GPIO 26, clean wiring for dual relay module
              Note: GPIO 25/26 are DAC outputs too but only used as GPIO

Boot-sensitive pins AVOIDED: GPIO 0 (boot mode), GPIO 2 (LED/strapping),
GPIO 12 (MTDI, affects flash voltage), GPIO 15 (MTDO).

Firmware Features
-----------------
  1. Multi-WiFi Fallback (WiFiMulti)
     Configured networks in priority order:
       1. Home Wi-Fi         (highest priority)
       2. Mobile hotspot    (fallback)
       3. Phone hotspot     (last resort)
     WiFiMulti.run() picks the strongest available SSID.

  2. mDNS Resolution
     Uses ESPmDNS to resolve "agritwin-fog.local" → Pi's IP
     No hardcoded IP needed — works even if Pi gets a new DHCP address
     MDNS.begin("esp32-agritwin") also registers the ESP32 on the network

  3. MQTT Publish (PubSubClient)
     Broker: agritwin-fog.local:1883
     Client ID: esp32_edge_001
     Topics published every 10 seconds:
       • agritwin/sensors         — full combined JSON payload
       • farms/001/sensors/temperature/data
       • farms/001/sensors/humidity/data
       • farms/001/sensors/light/data
       • farms/001/sensors/soil_moisture/data
     JSON payload includes: value, unit, timestamp (NTP), device_id, fw_version

  4. MQTT Subscribe — Relay Commands
     Topic: farms/001/commands
     Payload: {"command":"relay","relay":"pump","state":"on"}
     Callback toggles GPIO 26 or 25 and publishes state back

  5. OTA Updates (ArduinoOTA)
     Password: (set in firmware; change the default)
     Hostname: esp32-agritwin
     Uses ESP32 built-in ArduinoOTA library
     OTA partition table (partitions.csv):
       nvs        0x9000    20KB   — WiFi credentials, preferences
       otadata    0xe000     8KB   — tracks which OTA slot to boot
       app0 (ota_0) 0x10000 1.875MB — primary app
       app1 (ota_1) 0x1F0000 1.875MB — OTA update slot
       spiffs    0x3D0000  192KB  — future SPIFFS filesystem
     After upload: ArduinoOTA.handle() called in loop()

  6. Hardware Watchdog Timer (esp_task_wdt)
     Timeout: 30 seconds
     esp_task_wdt_init(30, true) in setup()
     esp_task_wdt_reset() called in every loop iteration
     If loop() hangs (WiFi lost, MQTT reconnect stuck, etc.), chip resets in 30s

  7. Auto-control Mode
     pumpOnThreshold: soil < 30% → pump ON
     pumpOffThreshold: soil >= 60% → pump OFF (hysteresis)
     lightOnThreshold: light < 20% → light ON
     lightOffThreshold: light >= 50% → light OFF
     Manual MQTT command overrides auto mode temporarily

  8. LWT (Last Will and Testament)
     Topic: farms/001/lwt
     Payload: "offline"
     Broker publishes this automatically if ESP32 disconnects silently

  9. NTP Time Sync
     Server: pool.ntp.org
     Timezone: IST UTC+5:30
     Timestamp included in every MQTT payload

Timing
------
  READ_INTERVAL  = 5000ms  (reads sensors every 5s)
  PUBLISH_INTERVAL = 10000ms (publishes every 10s)
  Can be updated at runtime via fog's Thompson Sampling adaptive algorithm
  (min 5s, max 60s) by sending set_interval command via MQTT

Build
-----
  PlatformIO env: esp32dev
  Framework: Arduino
  Libraries: PubSubClient, DHT, ArduinoJson, ArduinoOTA, WiFiMulti, ESPmDNS

  5. LAYER 2: FOG — RASPBERRY PI GATEWAY
────────────────────────────────────────────────────────────────────────────────

Hardware
--------
  Board: Raspberry Pi Zero 2 W
  CPU: 4-core ARM Cortex-A53 @ 1 GHz
  RAM: 512 MB
  OS: Raspberry Pi OS Lite (Debian 13 "trixie")
  Hostname: agritwin-fog.local
  IP: 192.168.1.7 (home Wi-Fi, DHCP reserved)
  Camera: Logitech C270 USB webcam → /dev/video0

Why Raspberry Pi Zero 2 W?
--------------------------
  • Runs full Linux — can run Mosquitto, InfluxDB, Python all simultaneously
  • Low power (~1.5W) — can run 24/7 on a small USB charger
  • WiFi built-in — no USB dongle needed (unlike Pi Zero 1)
  • $15 price point — cost-appropriate for a fog node
  • ARM64 — InfluxDB 1.6 has official ARMv7 builds
  • GPIO header — expandable for future sensors

Why not run everything on the ESP32?
-------------------------------------
  • ESP32 RAM (520KB) cannot run InfluxDB (needs ~50MB) or Python
  • ESP32 cannot buffer data across network outages (no filesystem suitable)
  • Separation of concerns — broker/buffer independent of sensor firmware

Mosquitto MQTT Broker
---------------------
  Port: 1883 (no TLS for local LAN — acceptable for private network)
  Config: /etc/mosquitto/mosquitto.conf
  Allow anonymous: true (internal network only)
  Persistence: yes — retains messages across broker restart
  Subscriptions from cloud: farms/+/sensors/+/data, agritwin/sensors

InfluxDB 1.6 (Local Time-Series Buffer)
----------------------------------------
  Port: 8086
  Database: agritwin
  Measurement: sensor_readings
  Tags: farm_id, device_id, sensor_type
  Fields: value
  Retention: 7 days (local buffer, cloud has permanent SQLite)
  
  Why InfluxDB 1.6 (not 2.x)?
  ARM32/ARMv7 support is best in 1.x — InfluxDB 2.x dropped ARMv7 support.
  Pi Zero 2 W is ARMv8 (64-bit) but Pi Zero 1 is ARMv6-only.

fog_server.py
-------------
  Role: MQTT subscriber → InfluxDB writer + cloud sync thread
  Subscribes to: agritwin/sensors, farms/001/sensors/+/data
  On message:  parse JSON → write to InfluxDB
  Sync thread: every 30s queries InfluxDB → POST to cloud /api/v1/sensors/ingest
  Handles: cloud unreachable (buffer locally), reconnect, deduplication

camera_service.py
-----------------
  Uses fswebcam to capture /dev/video0 → JPEG
  Every 5 minutes: POST /api/v1/camera/upload (multipart form data)
  Filename includes timestamp so images are chronologically sortable
  Cloud stores images in cloud/backend/camera_images/

Systemd Services (auto-start on Pi boot)
-----------------------------------------
  mosquitto.service     — MQTT broker
  agritwin-fog.service  — fog_server.py
  camera.service        — camera_service.py

Why fog layer at all? (not direct ESP32 → Cloud)
-------------------------------------------------
  • Local buffering: if cloud laptop is off, Pi keeps all data in InfluxDB
  • Reduced cloud dependency: sensors keep recording even without internet
  • Camera: ESP32 has a camera module (OV2640) but Pi USB webcam is higher quality
  • Future expansion: Pi can run TensorFlow Lite for edge AI
  • Protocol bridging: ESP32 uses MQTT; cloud HTTP API is REST over HTTP

  6. LAYER 3: CLOUD — FASTAPI BACKEND
────────────────────────────────────────────────────────────────────────────────

File: cloud/backend/main_working.py
Host: 0.0.0.0:8000 (accessible from all devices on LAN)
IP: 192.168.1.4 (laptop on home Wi-Fi)

Why FastAPI?
  • Automatic OpenAPI docs at /docs — every endpoint self-documented
  • Async Python — handles WebSocket + MQTT + HTTP concurrently
  • Pydantic validation — request/response models auto-validated
  • Lightweight — starts in <1s, runs on laptop without Docker
  • Better than Flask for async WebSocket support

Database: SQLite (data/sensor_history.db)
  Tables:
    sensor_readings   — farm_id, device_id, timestamp, temperature, humidity,
                        light_level, soil_moisture, raw_ldr, raw_soil, rssi,
                        free_heap, uptime
    twin_accuracy     — farm_id, timestamp, predicted/actual for soil/temp/humidity,
                        evapotranspiration, water_deficit, growth_stage,
                        calibration_triggered

  Why SQLite (not PostgreSQL)?
  • Single-file database — zero configuration, no separate server process
  • Sufficient for ~1 reading/10s = 8640 rows/day = manageable size
  • Portable — entire DB is one file, easy to back up
  • Python built-in — no extra pip package

Core Modules
------------
  core/sensor_storage.py
    • init_db()              — creates tables + indexes
    • store_sensor_reading() — INSERT with deduplication
    • get_latest_reading()   — SELECT most recent row
    • get_history()          — SELECT with time window + optional device filter
    • get_stats()            — aggregate min/max/avg

  core/mqtt_client.py
    • Subscribes to Pi broker: agritwin/sensors, farms/+/sensors/+/data
    • On message: parse JSON, build SensorReading, call store_sensor_reading()
    • Also triggers digital twin simulate_step() on each reading
    • Broadcasts to all WebSocket clients via asyncio.create_task()
    • Runs in a background thread (paho-mqtt is threaded)

  core/twin_accuracy.py
    • init_twin_accuracy_db() — creates twin_accuracy table
    • store_prediction()      — INSERT predicted vs. actual values
    • get_accuracy_stats()    — compute accuracy %, MAE, RMSE
    • get_physics_model_summary() — returns 6-model state + GDD + ET_mmday

API Routers
-----------
  api/v1/ai_assistant.py
    POST /api/v1/ai/chat
      • Calls Ollama HTTP API at localhost:11434
      • Injects live sensor readings + physics model context into system prompt
      • Response key: "reply" (not "response")
    GET /api/v1/ai/status → checks if Ollama is responding

  api/v1/camera.py
    GET /api/v1/camera/latest    → returns metadata of newest image
    GET /api/v1/camera/list      → paginated list of all images
    GET /api/v1/camera/image/{f} → serves image file as JPEG
    POST /api/v1/camera/upload   → receives multipart image from Pi
    POST /api/v1/camera/capture  → publishes MQTT command to Pi

  api/v1/twin_accuracy.py
    GET /api/v1/twin-accuracy/stats   → accuracy %, MAE, RMSE, sample count
    GET /api/v1/twin-accuracy/history → time-series for charting
    GET /api/v1/twin-accuracy/brain   → full DT Brain state:
        {
          twin_accuracy_pct, model_reliability_pct,
          gdd_accumulated_Cd,         ← GDD from actual temperature history
          physics_models: {
            1_soil_moisture_balance:  { ET_mmday, water_deficit_mm, status }
            2_evaporation_model:      { evap_factor, rate_label }
            3_plant_water_uptake:     { uptake_rate }
            4_light_influence:        { growth_stage, prediction }
            5_temperature_effect:     { effect_label }
            6_time_evolution:         { hours_until_stress }
          }
        }

  api/v1/metrics.py
    GET /metrics → Prometheus text format
    Counters: sensor_readings_total, mqtt_messages_received,
              twin_predictions_total, twin_calibrations_total
    Gauges:   twin_accuracy_pct, twin_avg_error

  api/v1/calibration.py
    Thompson Sampling adaptive interval:
    Explores different sampling intervals and exploits the best-performing one
    based on data utility vs. energy cost trade-off

  api/v1/multi_agent.py
    Multi-Agent System with:
      • IrrigationAgent  — decides when to water
      • LightingAgent    — decides when to adjust lighting
      • MonitoringAgent  — detects anomalies
      • CoordinatorAgent — resolves conflicts between agents
    Agents communicate via a shared message bus

WebSocket (/ws/{farm_id})
  • On connect: subscribe to farm_id broadcast channel
  • On sensor message: JSON pushed to all connected clients instantly
  • Dashboard uses this for <1s live updates
  • Flutter app polls HTTP instead (simpler, less battery drain)

CORS
  • Allows all origins (localhost:3000, 192.168.1.4:3000, mobile IP)
  • Required because frontend and backend run on different ports

  environment_insights_card.dart
    Physics calculations (all corrected):
    
    VPD (Vapor Pressure Deficit):
      svp = 0.6108 × e^(17.27 × T / (T + 237.3))  ← Tetens formula
      vpd = svp × (1 - H/100)
      Units: kPa; Thresholds: <0.4=Low, 0.4-1.2=Optimal, >1.2=High
    
    DLI (Daily Light Integral):
      Assumes 100% light ≈ 900 µmol/m²/s PPFD, 12h photoperiod
      DLI = (light% / 100 × 900) × 12 × 3600 / 1,000,000 = light% × 0.389
      Units: mol/m²/day; Thresholds: <10=Low, <30=Optimal, else High
    
    ET (Evapotranspiration):
      ET = 0.288 × (T + 17.8) × (light/100) × (100 - H)/100
      Calibrated: at T=28°C, H=62%, L=80% → ~4 mm/day
      Units: mm/day; Thresholds: <2=Low, <6=Normal, else High

  crop_health_widget.dart
    _rangeScore(value, optLow, optHigh, min, max):
      • If optLow ≤ value ≤ optHigh → score = 100
      • If value < optLow → linear scale from 0 (at min) to 100 (at optLow)
      • If value > optHigh → linear scale from 100 (at optHigh) to 0 (at max)
    
    Sensor ranges (% scale):
      Soil:     optimal 30-70, absolute 15-95
      Temp:     optimal 18-32°C, absolute 5-45°C
      Humidity: optimal 40-70%, absolute 20-95%
      Light:    optimal 30-80%, absolute 5-100%  ← uses % not lux
    
    Final score = soil×0.35 + temp×0.25 + humidity×0.20 + light×0.20
    Labels: ≥85=Excellent, ≥65=Good, ≥40=Fair, else Poor


────────────────────────────────────────────────────────────────────────────────
  9. DIGITAL TWIN PHYSICS ENGINE
────────────────────────────────────────────────────────────────────────────────

File: cloud/digital_twin/physics_model/comprehensive_physics.py
Called from: cloud/backend/core/mqtt_client.py (on every MQTT message)

What is a Digital Twin?
-----------------------
A Digital Twin is a real-time software model that mirrors a physical system.
In AgriTwin, the twin receives the same sensor readings as the real farm and
runs physics equations to compute values that are hard or expensive to measure
directly (water stress, evapotranspiration, crop growth stage).

The twin's predictions are compared to actual future sensor readings, and the
accuracy is tracked over time. If the twin drifts from reality, it indicates
the physics parameters need calibration.

Classes
-------
  SoilProperties
    field_capacity:      0.35 m³/m³  — soil holds 35% water at field capacity
    wilting_point:       0.15 m³/m³  — plants can extract water above this
    saturation:          0.45 m³/m³  — maximum water content
    bulk_density:        1.3 g/cm³
    rooting_depth:       0.30 m
    available_water_capacity() = (FC - WP) × depth × 1000  → mm

  WeatherData.from_sensors(sensors dict)
    Converts ESP32 sensor reading to weather data for physics equations:
      light% → solar_radiation (MJ/m²/day) via light_to_radiation()
      light_to_radiation: lux/500 = W/m², then ×12h×3600/1_000_000 = MJ/day

  WaterBalanceModel.simulate(weather, timestep_hours)
    The core water balance equation:
      M(t+1) = M(t) + I(t) - ET(t) - D(t)
      where:
        M = soil moisture (%)
        I = irrigation input (from pump relay state × rate)
        ET = evapotranspiration (Penman-Monteith, see below)
        D = deep percolation (drainage when M > field_capacity)

  WaterBalanceModel.calculate_evapotranspiration(weather)
    Simplified Penman-Monteith Reference ET (FAO-56 approach):
      Rn = net radiation (from solar_radiation)
      G  = soil heat flux (≈0 for daily)
      T  = mean temperature
      u2 = wind speed at 2m
      es = saturation vapour pressure = 0.6108 × e^(17.27T/(T+237.3))
      ea = actual vapour pressure = es × (H/100)
      Δ  = slope of saturation vapour pressure curve
      γ  = psychrometric constant
      ET0 = (0.408×Δ(Rn-G) + γ×(900/(T+273))×u2×(es-ea)) / (Δ + γ×(1+0.34×u2))
    Crop coefficient Kc applied: ETc = ET0 × Kc (Kc=1.0 for generic crop)
    Timestep scaling: ET_step = ETc × (timestep_hours / 24)

  simulate_step(sensor_dict, timestep_hours=0.17)
    Returns:
      {
        "water": {
          "moisture_percent",        ← predicted soil moisture
          "evapotranspiration",      ← mm for this timestep (~10min)
          "water_deficit",           ← mm of deficit vs field capacity
          ...
        },
        "crop": {
          "growth_stage",            ← "vegetative"|"flowering"|"fruiting"
          "gdd_accumulated",         ← GDD since tracking start
          ...
        }
      }

GDD (Growing Degree Days) Accumulation
---------------------------------------
  GDD_step = max(0, T_mean - T_base) × (timestep_hours / 24)
  T_base = 10°C (standard for most crops)
  Accumulated weekly from temperature history stored in twin_accuracy table:
    GDD_total = Σ max(0, T(i) - 10) × (0.17/24)  for all readings in window
  Milestones:
    Germination/Emergence: 0-100 GDD
    Vegetative:            100-500 GDD
    Flowering:             500-1000 GDD
    Fruiting/Maturity:     1000+ GDD

  Why GDD?
  Plants develop based on heat accumulation, not calendar days.
  A tomato in a heated greenhouse accumulates GDD faster than one outdoors.

ET → Daily Rate Conversion
--------------------------
  The physics engine produces ET per timestep (0.17 hours = ~10 min)
  For dashboard display: ET_mmday = ET_per_step × (24 / 0.17)
  This converts the per-step value to a standard agronomic mm/day rate

────────────────────────────────────────────────────────────────────────────────
  11. TWIN ACCURACY MONITOR
────────────────────────────────────────────────────────────────────────────────

File: cloud/backend/core/twin_accuracy.py

Purpose
-------
Quantifies how well the digital twin matches the real physical system.
Every time an MQTT message arrives (real sensor reading):
  1. The physics engine produces a prediction for that timestep
  2. The actual sensor values are the "ground truth"
  3. The error (| predicted - actual |) is stored in the DB
  4. Over time, we compute accuracy %, MAE, RMSE per model

Why track accuracy?
  • Digital twin drift detection — if error grows, physics params need recalibration
  • Calibration trigger — when RMSE > threshold, flag for recalibration
  • Trustworthiness metric — users see "65% accuracy" and know to trust/distrust
  • Research value — quantifies Penman-Monteith model quality for local conditions

Accuracy Formula
  twin_accuracy_pct = max(0, 100 - avg_soil_moisture_error)
  Where avg_soil_moisture_error is the mean absolute error in %

model_reliability_pct = same formula applied to multi-model aggregate

GDD Calculation in Backend
  • Queries twin_accuracy table for all readings in time window
  • GDD = Σ max(0, actual_temperature(i) - 10) × (0.17 / 24)
  • This is real GDD from real temperatures — not a prediction

ET Daily Rate in Backend
  • et_per_step from physics engine (mm per 0.17hr step)
  • et_mmday = et_per_step × (24 / 0.17)  ← consistent with FAO-56 daily units

────────────────────────────────────────────────────────────────────────────────
  14. PROTOCOLS USED AND WHY
────────────────────────────────────────────────────────────────────────────────

MQTT (Message Queuing Telemetry Transport)
  Port: 1883 (TCP)
  QoS: 1 (at least once delivery)
  Broker: Eclipse Mosquitto on Raspberry Pi
  Why MQTT:
    • Designed for constrained devices (IoT protocol, minimal overhead)
    • Publish/subscribe — ESP32 doesn't need to know cloud's IP
    • QoS 1 ensures messages delivered even if Pi temporarily unreachable
    • LWT (Last Will) mechanism for device offline detection
    • Retained messages — relay state persists across reconnects
    • 2KB per message — tiny overhead for sensor values
  Alternatives considered:
    • HTTP polling from ESP32 — higher overhead, not suitable for IoT
    • CoAP — less library support on ESP32
    • WebSocket from ESP32 — too complex, no broker layer

HTTP REST (FastAPI)
  Port: 8000 (TCP)
  Why REST/HTTP:
    • Universal — supported by Python, JavaScript, Flutter without custom libraries
    • Stateless — no connection management
    • JSON payloads — easy to debug with curl/Postman
    • Documentation via OpenAPI auto-generated
    • HTTP is human-readable in Wireshark for debugging

WebSocket
  Path: /ws/{farm_id}
  Why WebSocket:
    • Browser dashboard needs sub-1s updates
    • HTTP polling at 1s would be 86400 requests/day
    • WebSocket uses one persistent connection for push updates
    • Negligible protocol overhead after handshake

mDNS (.local hostnames)
  ESP32 resolves "agritwin-fog.local"
  Why mDNS:
    • No need to hardcode Pi's DHCP IP in firmware
    • Works on any router without setup
    • Standard RFC 6762 — works on macOS, Linux, Windows 10+

InfluxDB Line Protocol (Fog internal)
  fog_server.py writes to InfluxDB using line protocol:
    sensor_readings,farm_id=farm_001,sensor_type=temperature value=28.4 1710134596000000000
  Why line protocol:
    • Optimized for high-frequency time-series writes
    • Single TCP connection, streaming writes


────────────────────────────────────────────────────────────────────────────────
  15. HARDWARE: EVERY DEVICE AND EVERY PIN
────────────────────────────────────────────────────────────────────────────────

ESP32 DevKit (Espressif ESP32-WROOM-32)
  CPU:    Dual-core Xtensa LX6, 240 MHz
  RAM:    520 KB SRAM
  Flash:  4 MB SPI NOR flash
  WiFi:   802.11 b/g/n, 2.4 GHz
  BT:     Bluetooth 4.2
  Power:  3.3V regulated, USB 5V input via CP2102/CH9102 USB-UART

Pin-by-pin breakdown:

  GPIO 4   — DHT11 data pin
    Signal type: Single-wire digital
    Protocol: DHT proprietary (Maxim 1-Wire variant)
    Timing: 18ms start → 40-bit response (8-bit humidity int, 8-bit frac,
            8-bit temp int, 8-bit frac, 8-bit checksum)
    Pull-up: 10kΩ internal (DHT lib configures this)
    Max update rate: 1 Hz
    Power pin of DHT11: 3.3V (from ESP32 3V3 pin)
    Ground: ESP32 GND
    Why this pin: GPIO4 is not on ADC2 and not boot-sensitive

  GPIO 33  — LDR analog input
    Signal type: Analog voltage 0-3.3V
    Circuit: 3.3V → LDR → GPIO33 → 10kΩ → GND
    In bright light: LDR ~100Ω → GPIO33 near 3.3V → ADC near 4095
    In darkness: LDR ~1MΩ → GPIO33 near 0V → ADC near 0
    ADC1 channel 5 — 12-bit resolution (0-4095)
    attenuation: 11dB (full 0-3.3V range)
    mapped: (raw / 4095) × 100 = light percentage
    Why GPIO33: ADC1, not ADC2 (WiFi-safe)

  GPIO 34  — Capacitive soil moisture sensor analog output
    Signal type: Analog voltage (inverted — more water = lower voltage)
    Sensor: Capacitive (~$1 module), uses 555 timer oscillator
    Typical range: ~1.2V wet (soil saturated) to ~3.0V dry (air)
    Raw range: ~1476 wet to ~3680 dry at 12-bit ADC
    Calibration: map(raw, wetRaw, dryRaw, 100, 0) → soil %
    GPIO34: input-only (no internal pull-up/down available)
    ADC1 channel 6
    Why GPIO34: ADC1, input-only is fine for a sensor output

  GPIO 26  — Water pump relay
    Signal type: Digital output (3.3V logic)
    Relay module: KY-019 / 5V active-LOW relay
    Circuit: GPIO26 → 1kΩ → transistor base → relay coil (5V)
    Active-LOW: digitalWrite(LOW) = relay energized = pump ON
    Boot state: HIGH (pump stays OFF during boot)
    Pump: small 5V submersible pump, ~1A
    Why GPIO26: not boot-sensitive, not ADC2

  GPIO 25  — Grow light relay
    Same as GPIO26 configuration
    Grow light: 12V LED grow strip, controlled via 5V relay
    Why GPIO25: adjacent to GPIO26 (clean wiring), both are DAC-capable but
               used as digital GPIO here


Relay Wiring Detail
  Relay module pins: VCC, GND, IN, COM, NO, NC
  VCC → ESP32 Vin (5V from USB) or external 5V
  GND → common ground
  IN  → GPIO 26 or 25
  COM → +ve wire of pump/light power supply
  NO  → pump/light (Normally Open — circuit opens when relay OFF)
  NC  → not used

  When IN=LOW (ESP32 drives LOW):
    → Relay coil energized → COM-NO connected → pump/light ON
  When IN=HIGH (default):
    → Relay open → pump/light OFF


Raspberry Pi Zero 2 W
  SoC:   Broadcom BCM2710A1 (4x ARM Cortex-A53, 1GHz, 64-bit)
  RAM:   512 MB LPDDR2
  USB:   1x micro-USB OTG (camera + internet sharing possible)
  WiFi:  802.11 b/g/n, 2.4GHz (cypress CYW43438)
  Power: 5V 2A via micro-USB

  Logitech C270 USB webcam:
    Resolution: 720p (1280×720) at 30fps
    Interface: USB 2.0 (UVC class — plug-and-play on Linux)
    Linux device: /dev/video0
    Capture command: fswebcam -d /dev/video0 -r 1280x720 --jpeg 85 output.jpg


────────────────────────────────────────────────────────────────────────────────
  16. WHY EACH TECHNOLOGY WAS CHOSEN
────────────────────────────────────────────────────────────────────────────────

ESP32 (not ESP8266, not Arduino Nano, not STM32)
  • Dual-core, 240MHz — processes sensors + MQTT + OTA concurrently
  • Built-in WiFi — no external module needed (unlike Arduino)
  • ADC1 independent of WiFi radio (ESP8266 has similar ADC issues)
  • OTA update support built into Arduino framework
  • 4MB flash with OTA partition support (2 app slots)
  • $3-5 price — cheaper than Raspberry Pi for edge sensor node
  • Rich PlatformIO ecosystem — libraries for every sensor type

PlatformIO (not Arduino IDE)
  • Project structure: src/, include/, lib/ — proper software engineering
  • Multiple build environments (esp32dev + esp8266) in one platformio.ini
  • Native VS Code integration
  • Faster build caching than Arduino IDE
  • Unit testing support

Mosquitto MQTT (not RabbitMQ, not Kafka)
  • Tiny footprint — 100KB binary, runs on Pi Zero with 512MB RAM
  • MQTT protocol designed for IoT (low bandwidth, high latency tolerance)
  • RabbitMQ needs 128MB+ RAM just for broker
  • Kafka is for thousands of messages/sec — overkill for 1 sensor per 10s

InfluxDB 1.6 (not TimescaleDB, not InfluxDB 2.x, not SQLite on Pi)
  • Built for time-series — automatic time-based indexing
  • Handles bursts (ESP32 reconnects, sends lots at once)
  • ARM32 binaries available — InfluxDB 2.x dropped ARM32 support
  • Retention policy — auto-expires old data (7 days local buffer)
  • Why not SQLite on Pi: InfluxDB handles time-series queries 10x faster

FastAPI (not Flask, not Django, not Express.js)
  • Async — handles WebSocket + MQTT + HTTP concurrently without threading issues
  • Auto OpenAPI docs — every endpoint documented at /docs
  • Pydantic V2 for validation — catches malformed sensor payloads
  • Best performance among Python web frameworks (near Node.js speeds)
  • Modern Python type hints — IDE autocomplete throughout

SQLite (not PostgreSQL, not MongoDB)
  • Zero configuration — no server process, no installation
  • Single-file portability — sensor_history.db is self-contained
  • Sufficient for IoT scale — 1 reading/10s = 3 million rows/year ≈ manageable
  • Python built-in (sqlite3 module)
  • ACID compliant — no data loss on power failure

Ollama + LLaMA 3 8B (not OpenAI GPT, not Gemini)
  • 100% offline — data never leaves local network
  • No API key, no cost, no rate limits
  • LLaMA 3 8B: best open-source model at the time that fits in 8GB VRAM/RAM
  • Ollama: simplest way to run LLaMA 3 locally (one-command install)
  • Comparable quality to GPT-3.5 for simple Q&A tasks

Next.js 14 (not Create React App, not Vite, not Vue)
  • App Router: server components reduce client JS bundle
  • TypeScript by default — type safety with FastAPI response shapes
  • next/image optimization built-in
  • Fast Refresh for development
  • Production-ready: handles static assets, API routes, SSR

Flutter (not React Native, not Xamarin, not native Android)
  • Single Dart codebase for Android, iOS, Windows
  • Compiled to native ARM — no JavaScript bridge (React Native bottleneck)
  • Rich widget set — custom UI without platform limitations
  • Dart's sound null safety catches bugs at compile time
  • fl_chart: excellent charts library native to Flutter (better than Victory Native)

Recharts (not Chart.js, not D3, not Plotly)
  • React-native integration — works directly with React state
  • Responsive by default (no resize handlers needed)
  • Composable: Area + Line + Bar in same chart
  • Lighter than Plotly for simple line charts

Framer Motion (not CSS transitions, not GSAP)
  • React-first: animate based on state changes naturally
  • useScroll + useTransform: PlantDive scroll-linked animation
  • Spring physics: natural-feeling animations
  • Layout animations: elements animate when DOM changes

  20. GLOSSARY
────────────────────────────────────────────────────────────────────────────────

ADC1/ADC2   : Analog-to-Digital Converters on ESP32. ADC2 shared with WiFi.
              Use ADC1 for sensors when WiFi is active.

DLI         : Daily Light Integral. Total photosynthetically active radiation
              received per day. Units: mol/m²/day. Optimal for most crops: 10-30.

ET          : Evapotranspiration. Water lost from soil via evaporation + plant
              transpiration. Units: mm/day. Key metric in water balance models.

FAO-56      : UN Food and Agriculture Organization Paper 56 — the standard
              reference for Penman-Monteith ET calculation.

GDD         : Growing Degree Days. Cumulative heat units above base temperature.
              GDD = Σ max(0, T - T_base). Used to predict crop development stages.

IoT         : Internet of Things. Network of physical devices with sensors
              that collect and exchange data.

LWT         : Last Will and Testament. MQTT feature where broker publishes
              a message on behalf of a disconnected client.

MQTT        : Message Queuing Telemetry Transport. Lightweight publish-subscribe
              protocol designed for IoT devices over TCP.

mDNS        : Multicast DNS. Resolves hostnames like "raspberrypi.local"
              on local networks without a DNS server.

OTA         : Over-The-Air. Firmware updates delivered via WiFi rather than USB.

Penman-Monteith : Physics equation for reference evapotranspiration (ET0).
              Accounts for temperature, humidity, wind speed, solar radiation.
              Standard in agronomy (FAO-56 formulation).

PPFD        : Photosynthetic Photon Flux Density. Light available for
              photosynthesis. Units: µmol/m²/s.

QoS         : Quality of Service. MQTT delivery guarantees:
              0=fire-and-forget, 1=at-least-once, 2=exactly-once.

VPD         : Vapor Pressure Deficit. Difference between air's saturation vapor
              pressure and actual vapor pressure. High VPD = plant water stress.

Digital Twin: Real-time software model that mirrors a physical system,
              synchronized with live sensor data.

Fog Computing: Intermediate computing layer between edge devices and cloud.
               Provides local buffering, preprocessing, reduced latency.

Thompson Sampling: A Bayesian exploration-exploitation algorithm used here for
              adaptive sensor read intervals — balancing data quality vs. power.
